Ideas Index Java floor

Idea 0001 · build & compatibility · 2026-08-31

Lower the published Java floor from 21 to 17 — the audit says it costs one line

SpecBinder compiles with <release>21</release>, which makes JDK 21 the minimum a consumer must run: all three jars execute inside the consumer's own processes, and a JVM refuses to load class files newer than itself. Dropping the floor to 17 picks up the whole Java 17 LTS install base. The audit below found no dependency and no language feature standing in the way — every dependency is Java 8 bytecode, and the newest language features in use are records and instanceof patterns, both Java 16/17. Exactly one call site blocks it: a List.getFirst() in StepProcessor, which is Java 21.

Scope and status. Nothing here is implemented; this page records a proposal and the evidence for it, to be acted on later. The audit was run by inspection — greps over the three src/main trees and class-file version reads of the resolved jars — not by compiling with --release 17, which is the one step that settles it conclusively (see §6). The related latestSupported() change sitting in ## Unreleased is a prerequisite in spirit but not in code: it makes the floor and the ceiling independent, so this proposal touches only the floor.

1 · What the floor actually controls

--release N does two things: it compiles against the JDK N API, and it stamps the output class files as format N. The stamp is the part consumers feel, because it is enforced absolutely — no compatibility mode, no warning-and-continue:

UnsupportedClassVersionError: dev/specbinder/processor/AnnotationProcessor
has been compiled by a more recent version of the Java Runtime
(class file version 65.0), this version of the Java Runtime only
recognizes class file versions up to 61.0

What makes this bite harder for SpecBinder than for an ordinary library is that all three artifacts run inside the consumer's processes — there is no part of it that stays at arm's length:

ArtifactWhere it runs in a consumer's projectWhose JDK must satisfy the floor
annotationsOn their compile classpath.Their build JDK.
annotation-processorInside their javac process.Their build JDK.
execution-reporterAs a JUnit extension in their test JVM.Their test JDK.

So the floor is not a soft recommendation in a README — it is the exact set of teams who can adopt a new SpecBinder release at all. A team on JDK 17 today cannot upgrade past 2026.46.0; their only options are to move their whole project to 21 or stay pinned forever.

Compile low, run high. The floor is independent of the JDK that builds SpecBinder. --release 17 on a JDK 25 machine emits Java 17 bytecode and verifies no post-17 API was called. That verification is why --release is strictly better than the old -source/-target pair, which would happily let a Java 21 call through and produce a jar that explodes at the consumer's runtime instead of at our compile time.

2 · Where the floor is set today

Two places, and only one of them is live:

pom.xml · the real setting

<release>21</release>

On maven-compiler-plugin in the reactor root, inherited by every module. This is the one that decides the floor, for both main and test compilation.

annotation-processor/pom.xml · dead config

<source>21</source> <target>21</target>

Merged in alongside the inherited <release>, and ignored: when release is set the compiler plugin uses it and disregards source/target. It changes nothing today.

Delete the dead source/target rather than editing it

Leaving a second, silently-ignored copy of the version invites a future edit to the wrong one — change <release> in the root and the override still reads 21, suggesting a floor that isn't in effect. Worse, if the root <release> is ever removed, the override wakes up and applies -source 21 -target 21, quietly losing the API verification that --release was providing. There is no reason for that block to exist; the whole maven-compiler-plugin stanza in annotation-processor/pom.xml can go.

3 · Dependency audit — nothing above Java 8

A library can only go as low as its dependencies allow. The check is direct: read the class-file major version out of the resolved jar (major 61 = Java 17, 52 = Java 8). Every runtime dependency came back at Java 8:

DependencyVersionClass-file versionFloor imposed

The last row is the control that validates the method: SpecBinder's own published jar reads back as major 65, which is precisely the <release>21</release> we set. So the readings are trustworthy, and the floor is entirely self-imposed — no dependency is holding it up.

JUnit is the one worth calling out, because it is the usual suspect for a Java 17 baseline: Jupiter stayed on Java 8 bytecode across the whole 5.x line, and it is JUnit 6 that raises the floor to 17. On 5.14.1 there is no constraint. lombok is provided scope — build-time only, never on a consumer's classpath — so it is irrelevant to the floor, though it must independently stay new enough for whatever JDK builds SpecBinder.

4 · Language-feature audit — nothing above Java 17

Counts across the three src/main trees:

FeatureOccurrencesIntroducedSurvives --release 17?
Records20Java 16Yes
instanceof patterns18Java 16Yes
Text blocks6Java 15Yes
Sealed types0Java 17—
Switch type patterns0Java 21—
Record patterns0Java 21—

The newest thing actually in use is a Java 16 feature. Nothing in the codebase exercises the 21-only language surface, which is what makes 17 reachable at all.

This also fixes where the floor should stop. Going below 17 is a different proposition entirely: records, text blocks and instanceof patterns are 15/16 features, so a Java 11 floor would mean rewriting all 44 of those usages into constructor-and-getter classes, concatenated strings and casts. Java 17 is the floor that costs a one-line change; Java 11 is a refactor.

5 · The one real blocker

The language audit is about syntax; the API surface is a separate risk, because a Java 21 method call looks like ordinary code. The highest-risk family is SequencedCollection — getFirst(), getLast(), reversed() — added to List in Java 21 and very easy to reach for. One hit:

annotation-processor/src/main/java/dev/specbinder/processor/gherkin/StepProcessor.java:509

signatures.getFirst() — List.getFirst() is Java 21

List<ElementMethodUtils.MethodSignature> signatures = baseClassMethodSignatures.get(stepMethodName);
if (!signatures.isEmpty()) {
    return signatures.getFirst();   // -> signatures.get(0);
}

Replaceable with signatures.get(0) with no change in behaviour or readability: the receiver is a plain List out of a map, and the emptiness guard sits on the line immediately above, so index 0 is exactly as safe as getFirst() is. This is the “one line” in the title.

The same grep over the test submodule and the three examples/ modules came back clean — worth checking because --release in the reactor root governs test compilation too, so a Java 21 API call in a test would break the build just as surely as one in main.

Greps find the families you think to look for, which is why they are evidence and not proof. Post-17 additions are not limited to SequencedCollection — Math.clamp (21), HashMap.newHashMap (19), Objects.toIdentityString (19) and others were also checked and are absent, but the space is large. §6 is how you stop guessing.

6 · How to do it, and how the compiler finishes the audit

The point of --release is that it turns this from a research problem into a to-do list: compile against the JDK 17 API and every post-17 API call becomes an error with a file and a line number. Flip the flag, build, and read the list.

  1. Fix the known blocker

    signatures.getFirst() → signatures.get(0).

    annotation-processor/.../gherkin/StepProcessor.java:509

  2. Lower the floor, delete the dead override

    <release>21</release> → <release>17</release> in the reactor root; remove the maven-compiler-plugin stanza from the annotation-processor pom entirely (§2).

    pom.xml · annotation-processor/pom.xml

  3. Compile — this is the real audit

    A full reactor build, main and tests. Any remaining post-17 API call fails here by name. Expect either a clean build or a short list of mechanical substitutions.

    ./mvnw clean test-compile

  4. Verify the stamp landed

    Read the class-file major version back out of the built jars — it should be 61, not 65. This is the same check as §3 and it is worth doing: it confirms the flag took effect rather than being overridden somewhere unnoticed.

  5. Run the suite, then update the promise

    Bytecode level does not change behaviour, but the test suite is cheap insurance. Then the documented requirement — README.md says Java 21+, CLAUDE.md says Java 21+ — plus a ### Changed changelog entry.

    README.md · CLAUDE.md · CHANGELOG.md

7 · What it costs, and what it does not

Not a breaking change

Lowering a floor can never break an existing consumer

Every JDK that could load major-65 class files can load major-61. Reach only widens, so this needs no ⚠️ BREAKING marker and no special release handling — a plain ### Changed entry.

But it is a one-way door

Raising it again later is breaking

Publishing a floor is publishing a compatibility promise. Going 21 → 17 is free; 17 → 21 afterwards cuts off everyone who adopted in between. Worth choosing the number deliberately rather than drifting to it.

The standing cost is that SpecBinder's own source may not use Java 18–21 language or API features. After the one-line fix, nothing does — but it is a real constraint on future work, and the SequencedCollection methods are exactly the sort of thing that gets typed by habit. A CI job building on the floor JDK would catch that at the point it is introduced rather than at release time.

No effect on our own consumers either way: the ForgeApps workspace builds on JDK 25 and the IntelliJ plugin reads the reporter's JSON rather than linking the jar. This change is entirely about reach for other people — which is also why it is easy to keep deferring, and worth writing down instead.

8 · The ceiling, for contrast

Worth keeping the two straight, because they pull in opposite directions and are set in different places:

FloorCeiling
Set by<release> in the pomgetSupportedSourceVersion() in the processor
MeansMinimum JDK a consumer may runNewest -source the processor claims to handle
Want itAs low as the code allowsAs high as the running javac goes
Getting it wrongUnsupportedClassVersionError — a hard failureA javac warning on every consumer build
StatusThis page — 21, proposed 17Solved in ## Unreleased via SourceVersion.latestSupported()

The ceiling fix is what makes this page purely about the floor. A pinned RELEASE_n would have tied the two together — naming RELEASE_25 requires compiling against the JDK 25 API, so the ceiling would have dragged the floor up with it. Reporting latestSupported() instead — a method that has existed since Java 6, and therefore compiles fine under --release 17 — decouples them: the processor answers with whatever javac is actually running, 25 today and 26 later, while the floor stays wherever we choose to put it.
